# NEO Counter 0.17.0

Token payments can now be checked by an administrator using the same invoice verification control as BTC. Classic uses the explicitly Classic TokenScan JSON-RPC server; CP2 uses the Counterparty Core mainnet API. Neither falls back to the other ledger. Fixed read-only methods and fixed hosts prevent caller-selected RPC requests.

Checks require a ready mainnet parser caught up with the independently observed Bitcoin tip, valid send status, exact asset/atomic amount/source/destination, one matching destination send, matching transaction/block index, and matching parser/Bitcoin canonical block hash. Attach, move, detach and ambiguous multiple payments are held for review. Existing three-confirmation, invoice timing, immutable payload, unique payment claim and rollback rules apply. Bitcoin dust is never valued as a token payment. Token settlement trusts the selected public protocol parser; this is not local independent protocol validation.

After confirmed payment, inventory is read from that ledger for the exact bond/source address. An InnoDB stock row serializes reservations; each invoice has one unique reservation. Atomic quantities use asset divisibility from the node. Stale observations, source/asset mismatch or insufficient balance leave the payment claimed with HOLD_INVENTORY. A reservation is retained on reorg/recheck and never silently expires after a member paid. Repeated verification is idempotent. No release or delivery completion workflow is enabled yet. A fresh balance and payment recheck are required before any future signing/broadcast.

This is a confirmed-payment reservation system. It does not yet reserve inventory before presenting a payable invoice. Checkout remains explicitly LOCKED_NOT_PAYABLE, paymentsEnabled=false, automaticDelivery=false. A dedicated treasury signer, pre-payment reservation lifecycle, durable delivery worker, broadcast/reconciliation logic and funded end-to-end acceptance test remain necessary before enabling payment collection. The NeoMask community extension requires interactive approval and is not an unattended treasury signer. No keys or seed phrases belong in chat.

Validation: native PHP tests cover token asset/amount/source/status/send type/ledger/block hash/ambiguity rejection, real SQLite reservation uniqueness/capacity/idempotency/rollback/staleness, existing invoice/claim/queue rollback/replay/reorg/privacy rules, and rollback-only production schema probing. SQLite does not simulate MySQL concurrency scheduling; production uses InnoDB row locks. Existing JS and daily pricing PHP tests pass. Public Classic and CP2 endpoints returned matching Bitcoin block 972180 and the source PLEDGEBOND balance; no member payment or token delivery was made by these checks.

Primary API references: https://apidocs.counterparty.io/ and https://cp20-api.tokenscan.io/ (lists the distinct Classic and CP2 endpoints).
