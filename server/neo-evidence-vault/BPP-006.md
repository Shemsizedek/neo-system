# BPP-006: Synthetic Evidence Vault demonstration

Run with Node 24:

- `node --test server/neo-evidence-vault/*.test.mjs`
- `node server/neo-evidence-vault/demo.mjs`

The demo uses an in-memory database, a random ephemeral credential and a loopback HTTP listener. It creates synthetic evidence, reviews it and prints evidence and audit JSON. No real wallets, funds, personal records or external APIs are used.

## Authentication configuration

Protected endpoints return 503 when no credential is configured; `/health` and OPTIONS remain public. Invalid or absent credentials return 401. Roles are `read`, `ingest` and `review`; disallowed methods return 403. Credential records have `token`, `actor` and `roles`. Set `NEO_EVIDENCE_CREDENTIALS` to a JSON array of these records through the service secret manager. Tokens must be unique, nonblank secrets. This setting takes precedence over the legacy token, including when explicitly empty; malformed configuration throws.

The legacy `NEO_EVIDENCE_API_TOKEN` remains supported as a single service principal with all three roles, named by `NEO_EVIDENCE_ACTOR` or `evidence-service`. Its shared token cannot identify individual people. Use separate credentials for distinct accountable principals. `X-Reviewer` and body `reviewer` cannot set the recorded actor. Ingest input is restricted to evidence metadata; clients cannot supply an evidence ID or preapprove a record.

## Validation

Seven focused tests pass under Node 24.22.1: five new HTTP/configuration tests plus two existing store tests. The demo completed and emitted one reviewed synthetic record and two audit events. These results establish this local flow only, not production deployment, government qualification or a comprehensive security audit.

## Compatibility and release

Unauthenticated clients will stop working. Clients relying on supplied reviewer names will now be attributed to the configured credential actor. Existing databases need no schema migration. Inventory actual clients and configure secret credentials before deployment. This branch does not change production configuration.

Asset-level or tenant isolation, identity-provider integration, immutable audit retention, document digests, rate limiting and full input validation remain outside this patch. All read-role credentials can read all assets in this standalone service. Do not market it as a segregated multi-tenant service. Direct in-process store users remain responsible for their own authentication boundary.

Next gate: review and CI, then validate configured clients in staging before a separate deployment decision. No federal application or Bitcoin purchase is part of this change.
