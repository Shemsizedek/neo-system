# BPP-008: NEOpass session adapter and staging readiness

The optional `createEvidenceSessionAuthenticator` adapter reuses the existing NEOpass JWT verifier. It checks signature, issuer, mandatory timestamps, maximum lifetime and token use; rejects tokens scoped for another service; resolves active membership directly from the registry on every request; and applies independently configured subject grants for Evidence Vault roles. Token role/email claims never grant access.

Trusted server composition can pass the adapter to `createHandler(vault,{credentials:[],authenticate})` or `startServer({...,credentials:[],authenticate})`. Supply the authoritative registry's `getNEOpassCredential`, a server-only JWT secret, exact HTTPS allowed origins and explicit subject/role grants. Defaults do not activate session access. An unavailable registry returns 503 without exposing details. Empty or missing grants authorize nobody. Do not use the portal's emergency executive fallback to grant evidence privileges.

Browser session cookies are accepted only for GET, with Sec-Fetch-Site same-origin and an exact approved origin (Origin header, or the HTTPS request Host when Origin is absent). Duplicate session cookies are rejected. Cookie-only writes are denied; authenticated write roles require an explicit verified bearer session. This adapter does not mint or expose session tokens and does not change the login system. No long-lived privileged token should be embedded into a public frontend.

Staging requires a same-origin gateway/proxy preserving Host, browser fetch metadata and secure session cookie while forwarding the allowed Evidence Vault routes. Cross-origin cookie access is deliberately unsupported. The existing Explorer client can supply a runtime credential explicitly; an end-to-end portal session mount still needs deployment-specific wiring. Do not pass anonymous visitors through a shared privileged credential.
